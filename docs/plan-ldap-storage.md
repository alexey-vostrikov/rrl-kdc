# План: LDAP-хранилище конфигурации и ключей (фича `hdb-ldap`)

Статус: **решения приняты**, порядок зафиксирован. Обсуждение закрыто, открытые
пункты перечислены в конце.
Повод: интеграция с `rust-rest-ldap` («rrd»), вопрос о совместимости с Microsoft AD.

## Что проверено, а не предположено

1. **Heimdal уже умеет LDAP-хранилище, и его схема лежит рядом:**
   `~/DevOps/krb-src/heimdal/lib/hdb/hdb.schema`, OID-ветка `1.3.6.1.4.1.5322.10.*`
   (Padl). Атрибуты: `krb5PrincipalName`, `krb5KeyVersionNumber`, `krb5Key`
   (ASN.1 `Key` октетом, многозначный), `krb5KDCFlags` (целое, разрядность
   расписана в комментарии схемы и совпадает с `HDBFlags`), `krb5MaxLife`,
   `krb5MaxRenew`, `krb5ValidStart/End`, `krb5PasswordEnd`, `krb5EncryptionType`,
   `krb5ExtendedAttributes`; классы `krb5Principal`, `krb5KDCEntry`, `krb5Realm`.
   Комментарий в схеме: «this is temporary; keys will eventually be child entries
   or compound attributes» — то есть ключи в читаемом атрибуте это решение
   Heimdal, а не недоразумение.
2. **Потребитель уже публикует словарь AD:** `src/ad_schema.rs` в
   `~/DevOps/3part/rust-rest-ldap` — `userPrincipalName`, `sAMAccountName`,
   `userAccountControl`, `objectGUID`, `objectSid`, `servicePrincipalName`,
   `primaryGroupID`, `groupType`, `accountExpires`, `pwdLastSet`, классы
   `user`/`group`/`computer`, с настоящими OID Microsoft
   `1.2.840.113556.1.4.*`. Включается только в «kerberos mode» (когда задан
   keytab). `msDS-*` там сознательно нет.
3. **В AD ключи через LDAP не читаются.** Долговременные ключи Kerberos лежат в
   `supplementalCredentials` — бинарном блобе (набор свойств
   `Primary:Kerberos-Newer-Keys` и т.п.), который отдаётся только через DRSUAPI
   (`IDL_DRSGetNCChanges`, DCSync) и только с правами репликации; в зашифрованном
   виде `ENCRYPTED_SECRET` вместе с `unicodePwd`. Обычный LDAP-поиск его не
   возвращает.
4. **Разрядность `msDS-SupportedEncryptionTypes`** ([MS-KILE] 2.2.7):
   `0x1` DES-CBC-CRC, `0x2` DES-CBC-MD5, `0x4` RC4-HMAC, `0x8` AES128-SHA1-96,
   `0x10` AES256-SHA1-96, `0x20` FAST, `0x40` compound identity, `0x80` claims,
   `0x100` resource-SID-compression-disabled, `0x200` AES256-SHA1-96-SK,
   `0x400` AES128-CTS-HMAC-SHA256-128 (etype 19), `0x800`
   AES256-CTS-HMAC-SHA384-192 (etype 20). Для нашего профиля (17/18/19/20)
   это `0x18 | 0xC00` = `0xC18` без RC4 и `0xC1C` с RC4.

## Три разные вещи, которые легко слить в одну

Просьба «LDAP-хранилище, совместимое с AD» на деле распадается на три задачи с
разной ценой и разными рисками:

| Что | Совместимость с AD возможна? | Цена |
|---|---|---|
| **Словарь идентичности** (UPN, SPN, sAMAccountName, uAC, objectGUID, objectSid) | да, целиком | дни, половина уже есть в rrd |
| **Хранение ключей Kerberos** | **нет**: AD держит их в `supplementalCredentials`, недоступном по LDAP | надо выбрать свою форму (см. ниже) |
| **Хранение конфигурации реалма** | нет в AD (у него это реестр/GPO), есть у Heimdal (`krb5Realm`) и FreeIPA (`cn=kerberos`) | часы |

Отсюда главный вывод обсуждения: **«AD-совместимое хранилище ключей» — не
существует.** Совместимым с AD может быть словарь имён и правила, а форма
хранения ключей будет либо Heimdal-овская, либо AD-овский блоб, который мы сами и
придумаем проверять — то есть совместимость на словах.

## Что «AD-совместимость» здесь реально покупает и чего не покупает

Покупает: инструменты управления, которые ищут и пишут `userPrincipalName`,
`sAMAccountName`, `servicePrincipalName`, `msDS-SupportedEncryptionTypes`,
`msDS-KeyVersionNumber` (sssd, `realmd`, `adcli`, самбу-утилиты, скрипты
администратора), и клиентов, которые находят аккаунт по UPN/SPN, а не по DN.

Не покупает: участия в домене Windows. Для этого нужны `objectSid` с настоящим
распределением RID, PAC в тикете, `msDS-Behavior-Version`, DRSUAPI-репликация и
MS-KILE. Это отдельный продукт, а не фича хранилища, и в этом плане его нет.
Сказать это надо прямо, иначе ожидания разойдутся с результатом.

## Решение 1: где лежат ключи

Варианты:

1. **Heimdal-совместимый `krb5Key`** (OID `1.3.6.1.4.1.5322.10.1.10`), ASN.1 `Key`
   октетом, многозначный, kvno рядом. Плюс: поведение Heimdal — наша же
   спецификация, схема готова и читается глазами, ключи разных enctype лежат
   рядом, MIT-подобные каталоги понимают ту же идею. Минус: атрибут читаем любым,
   кому дан доступ → требует ACL на уровне атрибута (см. риски).
2. **AD-овский `supplementalCredentials`** — блоб `Primary:Kerberos-Newer-Keys` в
   формате `PASSWORDSET`. Плюс: единственная форма, которую прочитает настоящий
   AD/DRSUAPI. Минус: проверить нечем — второго AD у нас нет, свои же тесты будут
   проверять наш же парсер блоба; и в AD он всё равно не читается по LDAP, то есть
   преимущества «совместимости» внутри LDAP не даёт.
3. **Ключи только в keytab, в каталоге — ничего.** Плюс: ноль риска утечки.
   Минус: тогда KDC не может выпустить AS-REP: для проверки pre-auth нужен
   долговременный ключ клиента, а keytab — это серверная история. Годится только
   для TGS-половины.

**Решено: 1 + 3 как проекция.** Канон ключей — `krb5Key` по схеме Heimdal:
Heimdal и есть спецификация проекта, схема готова, ключи разных enctype лежат
рядом и читаются глазами. AD-овский `supplementalCredentials` делается **позже и
только на запись** — как проекция канона для инструментов, которые читают AD-блоб
(`impacket secretsdump`, самба), а не как место хранения.

Что это значит для реализации: две формы никогда не спорят, потому что у них
разные роли — `krb5Key` читается и пишется, блоб только собирается из записи.
Если блоб почему-то не собрался, учётка от этого перестать работать не может.

Формат блоба, чтобы не выдумывать при реализации ([MS-SAMR]):
`supplementalCredentials` — структура `USER_PROPERTIES` (§2.2.10.1); свойство
`Primary:Kerberos` — `KERB_STORED_CREDENTIAL` (§2.2.10.5), свойство
`Primary:Kerberos-Newer-Keys` — `KERB_STORED_CREDENTIAL_NEW` (§2.2.10.6), записи
ключей — `KERB_KEY_DATA` / `KERB_KEY_DATA_NEW` (§2.2.10.7). Пишем
`Primary:Kerberos-Newer-Keys` (уровень домена Win2008+), `Primary:Kerberos` — по
потребности читателя.

Приёмка этого куска честная только внешняя: наш кодек, проверенный нашим же
тестом, доказывает лишь симметрию. Пока независимого читателя в тестах нет,
статус куска — «экспорт, круговая проверка своим кодеком, внешняя приёмка не
проведена», и так и надо писать в README, а не «AD-совместимо».

## Решение 2: как говорить с каталогом

Варианты:

1. **Трейт без ввода-вывода + таблица соответствия** (мой выбор). Мы даём
   `hdb::ldap`: имена атрибутов, разбор и сборку значений, отображение
   `HdbEntry` ⇄ набор атрибутов, правила конфликтов. Сам обход каталога
   реализует встраивающий — у rrd это его же внутренние записи, у OpenLDAP —
   LDAP-клиент. Один маппинг, два драйвера, ноль зависимостей в крейте.
2. **Полный LDAP-клиент за фичей.** Плюс: работает против 389-ds/OpenLDAP без
   встраивания. Минус: тянет зависимость в KDC-крейт, и, главное, для rrd он
   бессмысленен — сервер пошёл бы по сети к самому себе.

**Решено: 1.** Маппинг и правила — у нас, обход каталога — у встраивающего.
Для rrd это ещё и единственный разумный вариант: каталог у него в процессе.

Отдельный подводный камень, который надо назвать сразу: **LDAP — это BER, а не
DER.** Наш `src/der.rs` намеренно строгий (минимальные длины, минимальные
INTEGER, отказ от не-DER) — он не разберёт чужой LDAP-ответ, где те же
необязательные поля разрешены в другом виде. Если когда-нибудь появится драйвер
2, ему нужен отдельный, терпимый BER-декодер; переиспользовать строгий нельзя, а
ослабить строгий — потерять проверки в протоколе Kerberos.

## Решение 3: канон флагов

Два словаря описывают одно и то же: Heimdal-овский `krb5KDCFlags` (битовая
раскладка в комментарии `hdb.schema`) и AD-овский `userAccountControl`
(`ACCOUNTDISABLE` 0x2, `LOCKOUT` 0x10, `DONT_EXPIRE_PASSWORD` 0x10000,
`TRUSTED_FOR_DELEGATION` 0x80000, `WORKSTATION_TRUST_ACCOUNT` 0x1000 и т.д.).

Правило: **в памяти живёт один `HdbEntry`, он и есть канон; LDAP — представление.**
При чтении значения собираются из обоих наборов; при записи пишутся оба. Если
наборы противоречат друг другу (в `uAC` стоит `ACCOUNTDISABLE`, а в
`krb5KDCFlags` нет `invalid`), запись **отвергается с внятной ошибкой**, а не
решается по вкусу: молча выбранное «побеждает AD» — это разошедшиеся KDC и
каталог, и обнаружится это на живом пользователе.

## Что это меняет в rrd (важнее самой фичи)

Чтобы KDC выпускал AS-REP, он должен **вычислить долговременный ключ клиента**.
LDAP обычно хранит `userPassword` как SSHA/хеш — из него ключ AES не вывести.
Значит:

* запись пароля становится **точкой генерации ключей**: смена пароля обязана
  одновременно положить `krb5Key` в запись;
* rrd сегодня меняет пароль через `ldappasswd` (RFC 3062 Password Modify). Если
  он станет KDC, а RFC 3062 не будет писать ключи, то после первой же смены
  пароля учётка тихо перестанет получать тикеты — и это будет выглядеть как
  «сломался Kerberos», а не «не обновили ключи»;
* это ровно та задача, которую AD решает хукком на `unicodePwd`: пароль задан →
  ключи пересчитаны. Совместимость тут семантическая, не побайтовая.

Поэтому в плане фича `hdb-ldap` идёт **вместе** с правилом «единственная точка
смены пароля»: `Admin::set_password` / `admin::rekey` уже вычисляют ключи, и
RFC 3062 в rrd должен звать их, а не писать хеш мимо.

## Риски

1. **`krb5Key` в каталоге = второе место, где лежит password-equivalent.**
   Требование к rrd: атрибут не отдаётся анонимному и простому bind, не попадает
   в выдачу по запросу всех атрибутов (`*`) и в `+`, доступ — только служебной
   учётке KDC. Это не пожелание, а условие включения фичи.
2. **Две формы одного факта** (`uAC` и `krb5KDCFlags`, `accountExpires` и
   `valid_end`, `pwdLastSet` и `pw_end`) — нужна таблица соответствия, проверенная
   по MS-ADTS и `hdb.h`, а не по памяти. Несовпадение семантики (`accountExpires`
   = «учётка истекает», `valid_end` = «principalka валидна») нельзя сглаживать
   молча.
3. **`msDS-SupportedEncryptionTypes` — это заявленный набор, а не набор ключей.**
   AD выбирает enctype для тикета по заявленному набору; у нас сейчас выбор идёт
   по фактическим ключам записи. Если каталог говорит `0xC18`, а ключей на 19/20
   нет, надо либо выпускать только по пересечению, либо отказывать — но не
   выдавать тикет в enctype, которого учётка «не поддерживает».
4. **SPN без реалма.** В AD `servicePrincipalName` = `HOST/server.example.com`,
   реалм подразумевается доменом; в keytab принципал всегда с реалмом. Маппинг
   `SPN + domain → principal@REALM` обязателен и должен быть покрыт тестом, иначе
   сервис не найдётся по тикету, который клиент просит по SPN.

## Объём

* маппинг `HdbEntry` ⇄ атрибуты, таблица конфликтов, тесты на каждую пару — 2–3 дня;
* схема (`krb5Principal`/`krb5KDCEntry` + `msDS-KeyVersionNumber`,
  `msDS-SupportedEncryptionTypes`) — полдня, половину словаря rrd уже отдаёт;
* разбор `krb5Key` (это наш же DER, `Key` уже кодируется) — часы;
* правило «пароль → ключи» в RFC 3062 на стороне rrd — отдельная работа rrd,
  не наша, но условие работоспособности;
* `supplementalCredentials` — не делаем.

## Чего в этом плане нет

DRSUAPI/репликация, распределение `objectSid`/RID, PAC, `msDS-Behavior-Version`,
FAST, PKINIT, S4U, реферралы. Всё это — либо отдельные продукты, либо уже
названные долги, и смешивать их с хранилищем нельзя: хранилище должно работать и
без них.

## Порядок (решено)

1. Закрыть текущую фазу: U2U, политика смены пароля, ACL в хранилище, API
   управления — коммитами.
2. REST API управления.
3. Фича `hdb-ldap` (этот план).
4. kadmin TCP (порт 749, RPCSEC_GSS) — последним и только если появится внешняя
   потребность: у rrd администрирование уже идёт через LDAP.

Причина такого порядка: REST и LDAP-хранилище оба стоят на API управления, и
делать их раньше значит дважды переделывать. kadmin стоит последним, потому что
это третий путь к тем же данным, а не новая возможность.

Экспорт в AD-блоб — после `hdb-ldap`, отдельным шагом, и он не блокирует ничего
остального.

## Открытые пункты

1. Таблица соответствия `uAC`/`krb5KDCFlags`, `accountExpires`/`valid_end`,
   `pwdLastSet`/`pw_end` — построить по MS-ADTS и `hdb.h` при реализации, а не по
   памяти. Пока её нет, маппинг не начинается.
2. Независимая приёмка AD-блоба: найти читателя, которому можно скормить блоб в
   тесте (самба-парсер как библиотека или `impacket`), иначе оставить статус
   «внешняя приёмка не проведена».
3. `msDS-SupportedEncryptionTypes` при расхождении с набором ключей: отказывать
   или выпускать по пересечению — решить на первом тесте с реальной учёткой,
   где каталог заявляет больше, чем есть ключей.
